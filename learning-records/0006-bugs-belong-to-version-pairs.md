# bug 属于版本对,不属于单件:dsh web「选工作区弹回」事故

用户 dsh web 无法新建会话/选工作区(创建即回滚)。直接原因是 dsh-context 0.33.1 的 contextTimeline 投影在空白会话上产出 `model/provider/contextWindow: undefined` 字段,违反宿主「转发事件参数必须无损 JSON」校验;但引爆开关是 8/29 23:20:08 的一次 `git pull --ff-only`(16 天架构差距一次到位:创建广播内嵌投影 + JSON 校验)。三条件(A 插件写 undefined、B 广播内嵌投影、C 校验抛错回滚)在 8/27–8/29 只有 A 为真故平安;pull 后全真,第一次创建(8/29 23:29 的 fa175ecb)即失败并留下与 9/4 完全同指纹的孤儿尸体。用户两次归因失误(先疑自己改 profile/palette;又惊讶「1.3k 星插件怎么会有 bug」「装好时明明能用」),经证据链(reflog 秒级时刻、projcache 成功记录、孤儿日志、npm 发布窗口 8/28–8/30)修正为「契约是双方签的,病出在配对」。修复:升级 dsh-context 0.41.3(上游 8/30 的 0.38.3 已修;`^0.33.1` 钉死收不到)。(2026-09-04;讲解 Lesson 0010)

## Evidence

- 用户原话:「我装好后就并未动过这个插件,并且我记得我刚刚装上这个插件时还可以开新对话来着」——记忆完全正确,有 8/27–8/29 五次成功创建的投影缓存物证;说明「时间上离故障近的改动 ≠ 原因」这条 LR-0002 锚点需要再强化一次:这次他怀疑的方向(自己的 profile 编辑、palette)仍然全部落空。
- 「1.3k 星的插件竟然有恶性 bug?」的惊讶,暴露 misconception:「好插件 = 不会坏」。修正后的观念应是:任何插件对「它出生时的宿主契约」负责;宿主收紧契约后,生态存在必然的适配窗口(本例 8/28–8/30,约两天)。
- 排查方法可复用:列案发时段在场者 → 逐个查不在场证明(备份 diff、文件 mtime、git reflog、npm 发布时间、会话日志指纹)。本次全部嫌疑(用户编辑 ×3、palette、mv-agent)都有不在场证明,真凶组合(旧插件 × pull)由 reflog 精确到秒定位。

## Implications

- 后续教 semver/依赖管理时,「^0.x 不跨次版本浮动」「宿主大升级后要手动推插件版本」是他亲历过的锚点,直接引用本次事故。
- 验收清单已 +2(Lesson 0010 第 5 节):宿主大 pull 后必做「新建会话」冒烟(打开旧会话不经过创建链路);检查被 ^0.x 钉住的插件新版本。
- 尚未验收的技能:能否独立复述「三条件各自的提供者与转真时刻」;下次课开头用 quiz ① 检验,过了才确认内化。
- dsh 维护者视角的后续(fail-loud 边界、UI 静默 catch、投影校验前移)他已表示兴趣,可作为「指挥 AI 改宿主」的第一个真实 ticket 候选。
