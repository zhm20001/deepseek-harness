# 卡点不在架构概念，在 JS 语言层——「不需要再教 Cordis 内部机制」这条推论被推翻

2026-09-24 会话。用户主动要求「从底层 cordis 源码学起，掌握 agent 设计与架构」。第一轮按仓库既有文档口径讲节点 1（Context / inject / FiberState / dispatch mode，带大量 `file.ts:line` 引用），用户明确回答「我还是没懂，你假定我没看过源码且没有基础」。

重讲后当场暴露出真实的缺失层不是架构概念，而是**读代码的语言层**：

- 不知道 `ctx.tools` 是一个「从盒子里取标签为 tools 的格子」的表达式，也不知道 `ctx` 是 context 的缩写。
- 把「文件路径 `vendor/cordis/src/context.ts`」和「代码表达式 `ctx.tools`」看成同一类东西，要求先立消歧约定才能继续。
- 不知道 Proxy、`inject` 「声明」、服务、fiber 之间谁主动：自己给出的卸载链条是「ctx 向登记板发信号，调用 ctx.effect 收回插件」——方向反了；并说出「fiber 是一系列事件的集合」——事件名单的所有权反了。

补语言层之后推进很快：用户自己把 `Fiber` 对上数学的纤维丛（fiber bundle），并给出「纤维随基点变化」的直觉；互等死锁一题第一轮就答对（「锁死。因为声明的能力达到之前，插件不能工作，所以谁也不能工作」）。

## Evidence

- 主动要求把「服务/事件/fiber/插件」先定义再讲关系，且要求用比喻 + mermaid 时序图；接受度明显高于表格化的文档口径。
- 对**实测证据**反应最好：三次 `node --import tsx/esm` 现场跑真源码（环依赖 → 两个 fiber 状态停在 0 且全程无异常；五种 dispatch 的带毫秒输出）后，才出现「OK」并主动要求总结。
- 自行指出 `Fiber` 与纤维丛的关联，说明抽象代数词汇对他不是负担；负担是 JS 语法本身。
- 两道 dispatch mode 自检题（事件选型走决策树、bail 为何短路）尚未作答，用户改口要求先做集合总结。

## Implications

- 推翻 LR 0001 的推论「不需要再教 Cordis 内部机制」：那条只在「概念地图」层面成立，一旦要求读到具体表达式就立刻失效。以后凡引入新文件，先给语言层解码规则，再给机制。
- 固定这套讲法：消歧约定 → 盒子/格子/点号 → 术语定义表 → 因果链推导（不用记忆负担换术语）→ 现场实跑 → mermaid → 自检题。引用源码位置一律写成「文件 X 第 N 行」，避免与代码表达式撞脸。
