Cordis 五个核心概念

来源：docs/cordis-primer.md。dsh 的「一切皆插件」建立在被 vendor 进来的 Cordis DI 框架上。

plugin ≈ Service
插件不是一段被动的钩子代码，而是一个服务：挂载后把自己的能力注册进 context,别的插件按名字取用。例：super(ctx, 'agentLoop') 注册了 ctx.agentLoop。
context = service repository
ctx 是服务仓库,每个插件收到自己的 ctx 视图;服务出现/消失时依赖它的插件会被启动/暂停。
inject 声明依赖
static inject = ['llm', 'tools', ...]:依赖的服务全部就位前,插件的 fiber 一直 pend(挂起等待),不会启动。
typed events
插件间通信:emit(单向)、waterfall(链式改写,必须调 next())、parallel/serial。通过 declaration merging 扩展事件表。
registrations are effects
一切注册都走 ctx.effect() / ctx.on(),返回 disposer——插件卸载时注册自动撤销,系统始终可逆。

启动组合层叠(自下而上)

来源:docs/architecture.md 与 apps/cli/src/profile-boot.ts。关键事实：root 配置是一个空列表——「dsh 产品」不存在于代码里,只存在于组合结果里。

0root entry list — 空。没有任何内置插件。
1bundle patch layers — 按 dsh.profile.bundles 顺序应用,如 dsh-base → dsh-headless(base/cordis.patch.yml 有全部行)。
2profile patch — $DSH_HOME/profiles/<name>/cordis.patch.yml,热重载。
3home patch — $DSH_HOME/cordis.patch.yml,用户级。
4--patch overlays — 一次性命令行覆盖,最高优先级。

patch 行可写 disabled: !!js <表达式> 来按条件拔掉任何插件(包括 agent-loop)。

Patch 行语法

patch 是一个 YAML 文件,只做三种动作。真实样本:dsh-headless 的 patch(改配置 + 禁用 + 追加)与 examples/web-schedule/cordis.yml(纯追加的用户 overlay)。

动作写法含义
改配置- id: <行id> + config:按 id 定位已存在的行,整体替换其 config(不深合并)
禁用- id: <行id> + disabled: true从组合中划掉该插件;可写 disabled: !!js <表达式> 按平台/环境条件禁用
追加- insert: + 新行列表插入新插件行,每行含 id(后续 patch 的定位键)、name(npm 包名)、可选 config/inject

规则:同一 id 后写的层赢;行顺序本身无加载语义(激活由服务可用性驱动);config 与 disabled 的值可用 !!js 表达式读环境变量、process.platform、甚至 ctx.<service>。base bundle 就是一次性对空 root 的大 insert。

外部插件装载路径(仓外代码怎么进组合)

路径写法适合
patch 行绝对路径name: /abs/path/to/plugin-dir开发期:tsx 直载 TS 源码,免 build,改完即生效
dsh plugin add本地路径装进 profile日常自用:进 $DSH_HOME,随 profile 启停
npm 包名name: '@deepseek-ai/dsh-<pkg>'正式分发:走 node_modules 解析

仓外插件里 import '@deepseek-ai/dsh-<pkg>' 这类裸包名要能解析到 harness 源码树,靠插件包 node_modules 里的 link: 依赖指向 harness 包目录——同一 realpath 同一模块实例,与仓内共享服务注册表,无版本漂移。边界提醒:仓外插件不要发自定义 session 事件——事件类型不在持久化重载的白名单里,落盘会让会话日志重载被拒;可重建性用标准 tool 事件(参数/结果)承载。

Turn flow(agent-loop 的一次循环)

来源:packages/core/agent-loop/src/agent.ts(ReactLoopAgent)。

wakeDriver → kick()  while (await this.turn()) {}
  turn()        记 turn/start
    preStep()   认领输入, ctx.systemPrompt.assemble 组装 prompt
    step()      ── 内层循环 ──
      buildRequest()   agent/request waterfall(插件可改写 provider/model)
      llm.stream()     流式返回 → assistant/message
      有 tool-call?    无 → turn completed;有 ↓
      executeToolCalls()  有界并行池、独占屏障、按模型顺序回填
    step/end → turn 停止条件判断 → turn/end

三方分工(bundle / leaf / app)

来源:packages/examples/agent-spine-demo README。

  • bundle(spine):agent 需要的共享插件集——Timer、LlmRuntime、SessionStore、SystemPrompt、ToolRuntime、AgentRegistry,最后挂 ctx.plugin(AgentLoop, …)。
  • leaf(如 examples/headless-agent/cordis.yml):声明后端——LLM adapter、bash 执行器、持久化、要哪些 tool。
  • app:入口程序(CLI / ACP / JSON-RPC)。

「拔掉 agent-loop」的失败时间线

  1. 启动、加载其余插件:一切正常。inject 驱动的服务没出现只会让依赖者 pend。
  2. 没有人调 ctx.agents.setFactory(),工厂槽位为空。
  3. 直到有入口调 agents.create(…) → 抛错 "no agent factory registered (load an agent-loop plugin)"(packages/core/agent/src/index.ts:392)。

结论：失败是惰性的、按需的,而且错误信息直接告诉你该装回什么。
