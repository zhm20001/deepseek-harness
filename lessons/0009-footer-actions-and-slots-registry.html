Lesson 0009 · dsh slots 体系

footer 动作区与 slots 注册表——UI 是一张可以查询的名单

目标:15 分钟。搞清 palette 按钮住的「footer 动作区」是什么、slots 注册表怎么把界面变成数据;分清 palette 卡片的两条点击路;学会验收「发现/枚举界面内容」类功能时的第一问。
你的原话:「直接寻找 slots 才是扫描的正道。我制作这个 palette 本身的逻辑也是 for plugin,理应直接指向 slots。但为什么第一次没有直接找到 slots 而是扫全局?我很奇怪。」——这一课就把这句话变成你的固定判断力。

1. 先说 payoff:验收这类功能,第一问是「数据源是注册表还是 DOM?」

palette v1.8 的「扫描」按钮为了发现页面上有什么,把整个 DOM 翻了一遍,结果连「进入某个 session」的条目都扫了进来——因为那也是「页面上能点的东西」。v1.9 改成只读 slots 注册表,问题消失。

这不是实现细节的运气,是一条通用规律:宿主把扩展点做成「登记处」时,登记处本身就是最准的数据源。dsh 的每一个 slot 都是一个登记处——插件注册 UI 时留下的是结构化数据(id、label、顺序),不是像素。以后你指挥 AI 做「列出/发现/枚举界面上有什么」的功能,第一句话就该问:「宿主有没有现成的注册表可读?还是真的只能从 DOM 里捞?」palette 这次撞的坑,就是没先问这句话。

2. slots 注册表:注册即登记,UI 是一行数据

客户端插件注入 ctx.inject(['slots']) 后,用一对参数登记 UI:

ctx.slots.register(options, Component)

对 list 类 slot(palette 按钮所在的 footer 动作区就是),options 长这样:

{ name: 'sidebar.footer.action', id: 'palette-board', label: () => t('footerButton') }
  • id:这一项的身份。可选——别的插件可以不填,这是后面「文字匹配」伏笔的根源。
  • label:显示名。可以是字符串,也可以是函数(thunk)——每次渲染重新求值,所以切换语言后按钮文字会自动跟着变。这个优点同时是 footerTrigger 卡片的弱点,见第 5 节。
  • order:同 slot 内的排序。

两条对读代码很关键的纪律(注册表实现:packages/client/ui-renderer/src/client/registry.ts:95,SlotRegistry extends Service):

  • slot 的存在跟着声明者走:一个 slot 只有在声明它的宿主组件挂载时才存在。侧栏不在,footer 动作区就不在。
  • 注册表是可枚举的公共服务:不只是「往里写」,还有公开的读面——registry.ts:366 的 entries(key) 给原始名单(带 label),registry.ts:379 的 entriesOfSlot(key) 给「影子竞争」后的现役胜者名单。palette v1.9 的扫描正是调的 ctx.slots.entriesOfSlot('sidebar.footer.action')。

换一个角度:第 8 课讲的是 UI 的「呈现形态」,这一课讲的是 UI 的「登记形态」。形态给用户看,登记给程序读。一个功能若要跨插件发现别的 UI,走登记、别走像素。

3. footer 动作区:palette 自己就住在那里

打开 packages/client/ui-sidebar/src/client/SidebarRoot.tsx:213,侧栏的「脚」是这么写的:

<div className={css.footerActions}>
  {renderSlot('sidebar.footer.action', { wide })}
</div>

宿主在 packages/extensions/cordis-client-runner/src/client/slot-catalog.ts:1988 给这个位置立了正式户口:

key: sidebar.footer.action · kind: list · summary: "Optional actions beside Settings at the sidebar foot."(Settings 旁边的可选动作,每个插件登记一项)

所以这个区域的规矩是:宿主只出一块地,谁想加按钮谁登记。palette-board 的 client 半(src/client/index.tsx)调 ctx.slots.register 把自己的圆形按钮放进去;侧栏设置、别的插件,同样各占一行。你点开 palette 时,那个按钮就是从这张名单里渲染出来的。

顺带一提,这份 slot-catalog 是宿主发布的全部 slot 的编译期清单——每个 key 的类型(list/single)、谁声明、登记选项、示例代码都在。验收「往哪儿挂 UI」的问题时,它就是官方答案,不用翻 DOM 猜。

4. 两条点击路:link 卡片与 footerTrigger 卡片

你在第 3 问里疑惑的「卡片触发到底是谁写的」,答案是:两条路一直并存,谁也没改谁。它们恰好落在第 8 课那条主轴的两端:

link 卡片(链接卡)footerTrigger 卡片(收编卡)
怎么来的你亲手在注册弹窗里填「页面链接」点「扫描」从 footer 注册表里收编
存什么一个 URL 字符串目标按钮的 label 文字
点击时window.open(url) 开新标签页在 footer 区域找到那个按钮,调 .click()
主轴位置新 browsing context(第 8 课右支)同 document,真按钮、真处理器(左支)

link 卡片自第一版就有,从未变过。footerTrigger 是沙箱时代就存在的另一条路:扫描发现的 footer 动作「一键收编」成卡片,之后每次点击都等价于替你按了那个真按钮——同 document,函数调用级精确。

5. 口径同源:扫描看见的世界 = 触发能点的世界

footerTrigger 的触发实现(src/client/catalog.ts 的 findFooterButton)有个刻意的限制:只在 footer 动作区里找,找不到就报「未找到」,绝不扩大到全页。为什么?因为它靠文字匹配定位按钮,而注册表的 id 是可选的、渲染出来的 DOM 又不带 id——文字是唯一现成的桥。若允许全页找,同名文字会点错对象。

于是 v1.9 立了这条纪律:扫描的口径(footer 注册表)= 触发的口径(footer 区域)。扫描时从名单里看到的,触发时就在同一块地里找;区间不扩大,误伤就不发生。

诚实边界:文字匹配有一个已知弱点——label 是 thunk,切换语言后按钮文字变了,旧卡片存的旧文字就找不到按钮(卡片失效,需重新扫描收编)。而 link 卡片存的是 URL,不受影响。这不是 bug,是「id 可选」现实下的取舍;要根治,得等宿主把 id 透出到 DOM。

6. 复盘:为什么 v1.8 先扫了 DOM?

你的疑问值得正面回答。当时的推理链是:①目标被表述成「发现页面上已有的按钮」——字面上指向 DOM;②想当然认为 slots 注册表是「给我们写进去的」,没验证它有没有公开的读面;③DOM 扫描看起来最通用,就先做了。错在 ②:没读注册表的源码就假设它只写不读。事实上 entriesOfSlot 一直是公共服务,读一行名单就能拿到带 label 的现役清单。

把教训抽成一句你以后可以直接拿来指挥 AI 的话:

「做发现类功能之前,先找事实的源头。有注册表读注册表,没有才碰 DOM——并且把『为什么没有』问清楚。」

DOM 是渲染的结果,注册表是事实的源头。从结果反推源头,永远比直接读源头又慢又脏——这就是 v1.8 → v1.9 的全部故事。

7. 检验你的理解

① palette 的「扫描」要列出侧栏 footer 里现有哪些插件按钮,正确的数据源是?

注册表是现役名单:谁挂载谁在,还带 label。DOM 是渲染结果,会把 session 条目等无关可点物一起捞进来(v1.8 的坑);手工清单是第二事实源,会和真页面漂移。

② footerTrigger 卡片点击时为什么只在 footer 区域找按钮,不扩大到全页找同文字?

口径同源:扫描从 footer 注册表看到谁,触发就只在 footer 地里找谁,区间永不扩大。文字匹配没有 id 可靠,围栏越小越不会点错对象。

③ 一张 footerTrigger 卡片在切换界面语言后点不动了,最可能的原因是什么?

label 是每次渲染重新求值的函数,切语言后按钮文字变了;卡片按文字找按钮,旧文字自然落空。link 卡片存 URL,不受此影响——这是文字匹配路线的已知边界。
