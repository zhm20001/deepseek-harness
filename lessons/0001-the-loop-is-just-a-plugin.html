Lesson 0001 · dsh 架构

Loop 只是一个插件——而这正是它还能工作的原因

目标:10 分钟内搞懂「一切都是插件」的真正含义,以及拔掉 agent-loop 后系统到底会发生什么。
你的原话:「如果把底层的 loop『拔掉』,岂不是直接把主功能破坏了?那还怎么正常工作呢?」
这节课就回答这一个问题的三层答案:没有什么被"破坏"、失败是惰性的、这个设计恰恰是为了让你能换 loop。

1. 先纠正一个直觉:不存在「拔掉就坏」的内核

大多数框架有一个不可拆卸的内核,外围才是插件。dsh 的答案更激进:root 配置是一个空列表(apps/cli/src/profile-boot.ts 中的 PROFILE_ROOT_CONFIG)。代码里没有一行写着「启动时必须加载 agent-loop」。你运行的那个「dsh」,是启动时把四层 patch 叠出来的组合结果:

空 root
 ← bundle patches(dsh-base → dsh-headless …)
 ← profile patch($DSH_HOME/profiles/<name>/cordis.patch.yml)
 ← home patch($DSH_HOME/cordis.patch.yml)
 ← --patch overlays(命令行一次性)

每一行 patch 只是往清单里加/改/禁用插件行。所以「dsh 产品」不在代码里,在组合层叠里——这是第一个心智模型转变。

2. agent-loop 究竟是个什么插件?

看真实代码(packages/core/agent-loop/src/index.ts:296):

export class AgentLoop extends Service implements AgentFactory {
  static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt']
  constructor(ctx, config) {
    super(ctx, 'agentLoop')          // 贡献服务 ctx.agentLoop
    ctx.effect(() => ctx.agents.setFactory(this))  // ★ 关键一行
  }
}

两件事读出设计:

  • inject:它消费五个服务——agent 注册表、会话、LLM、工具、system prompt。依赖没就位它就一直 pend,不启动。
  • ctx.agents.setFactory(this):它贡献自己的唯一方式,是把自己注册成 AgentFactory。也就是说:packages/core/agent 里的注册表只认「工厂」这个接口,根本不知道有哪个具体 loop。

真正的循环(模型调用 → 工具调用 → 重复)在 agent.ts 的 ReactLoopAgent 里:kick() 里的 while (await this.turn())。它只是工厂造出来的默认实现。

3. 拔掉它:失败时间线

现在把 patch 里那行 agent-loop 标成 disabled: true。逐时刻推演:

时刻发生什么
启动完全正常。其余几十个插件照常挂载。没有任何代码「要求」loop 存在。
等待期没有任何人调 setFactory(),ctx.agents 的工厂槽位保持 undefined。系统不崩溃、不报警。
有入口调 agents.create(…)此刻抛错:no agent factory registered (load an agent-loop plugin)(packages/core/agent/src/index.ts:392)

三个要点:

  • 惰性失败:错误只在真正需要造 agent 时发生。会话、持久化、settings、工具——全都照常工作。这不是「主功能被破坏」,而是「这项能力暂时无人提供」。
  • 错误信息即诊断:报错直接告诉你解法——装回一个 agent-loop 插件。这是 dsh 的约定「misconfiguration fails loud」。
  • 空位就是邀请:那个空着的工厂槽位,任何插件都可以填。这正是问题第三部分的伏笔。
为什么这样设计? 因为「Agent 的循环策略」本身就是个可替换决策:ReAct 循环、单轮问答、计划-执行分离、带审批闸门的循环……dsh 把它建模成一个接缝(AgentFactory),默认实现叫 dsh-agent-loop。「loop 是插件」不是为了炫技,是为了让你能不动其他 50 个插件地换掉它。

检索练习

不翻上文,凭记忆回答。点击选项立即得到反馈。

Q1. 把 agent-loop 从组合里禁用后,dsh 启动的那一刻会发生什么?

启动完全正常。root 是空列表、没有代码强制要求 loop;只有当某个入口真正调用 agents.create() 时才会抛 no agent factory registered。

Q2. agent-loop 插件向系统贡献能力的唯一关键动作是哪一行?

ctx.effect(() => ctx.agents.setFactory(this))。它把自己注册成 AgentFactory;注册表只认接口,不知道具体实现。

Q3. 你想完全换掉默认 loop(比如换成单轮问答),正确的做法是?

接缝就是为此设计的:实现 AgentFactory(接口在 packages/core/agent/src/index.ts:178)并调 ctx.agents.setFactory(this),其余插件零改动。下一课我们动手做。

动手验证(强烈推荐,共 5 分钟)

  1. 在仓库根跑 dsh --profile headless --dump-config(或 pnpm dsh …),在输出里找到 agent-loop 那一行——亲眼看到「产品 = 一份组合清单」。
  2. 打开 examples/headless-agent/cordis.yml,找出是哪几行让它成为一个完整 agent(提示:LLM provider 行、agent-spine 行、backends 行)。这个文件就是最小可运行组合的活样本。
  3. 进阶(可选):写一个只含 - id: agent-loop / disabled: true 的小 patch 文件,用 --patch 挂上,跑一次任务,观察报错出现的位置和内容是否与本课预测一致。

本课收获

  • root 是空列表;「dsh」是四层 patch 叠出的组合结果。
  • agent-loop 靠 inject 消费五服务、靠 setFactory 贡献自己。
  • 拔掉它是惰性失败:启动正常,agents.create() 时才报 no agent factory registered。
  • 空着的工厂槽位 = 你 DIY 的入口。
