从源码到命令:你的 dsh 为什么停在 0.1.0-rc.5

目标:15 分钟后,你能把「源码 → 能敲的命令」画成一条四层管线;能解释为什么 git clone 不自带 dsh 命令、npm 安装却"自带";每次追更后,知道用哪条命令验收哪一层——以及哪一层永远不会自己跟上。
继续用你的真实事故教学。2026-08-29:GitHub 显示新版本,而 dsh --version 依旧是 0.1.0-rc.5。调查发现这是两处互相独立的错位叠在一起:仓库的 pull 其实没成功,而全局命令是另一份冻结拷贝。你修插件是作者,管自己机器是运维——这节课把运维这半边补上。

1. 事故还原:两处独立错位

当时的三个事实,先摆出来:

  • 仓库层:本地 HEAD 停在 0.1.0-rc.5 的提交上,git fetch 后比对——落后 origin/master 1933 个提交。你"执行过 pull",但本地有两个被修改的文件,跨 1933 个提交的合并碰到它们会被 git 拒绝执行;拒绝信息只打印在当时那屏输出里,没看到就等于没发生。
  • 命令层:全局 dsh 是 8 月 22 日你手动打包后 pnpm add -g 装进去的。安装的是当时的完整拷贝——之后仓库怎么变,都与它无关。
  • 发布节奏:GitHub master 已到 0.1.2-alpha.1,而 npm 上最新只到 0.1.1-rc.2——master 领先 npm 是常态,不是异常。

修复动作(当天已完成):丢弃脏文件 → pull(快进 1933 提交)→ install + clean + build → 删掉冻结拷贝,全局命令改为指向仓库构建产物。要理解这套修复为什么长这样,需要一个模型。

2. 名词卡:命令 = PATH 上的一个可执行文件

先破除最大的神秘感。你在任何目录敲 dsh 回车,shell 做的事毫无魔法:

拿环境变量 PATH(一串用冒号分隔的目录),按顺序逐个找名为 dsh 的可执行文件,找到第一个就运行它。(机制见 PATH (variable))

所以"注册一个命令"翻译成机械动作就是:把一个可执行文件,放进 PATH 上的某个目录。仅此而已。证据就在你机器上,亲手看:

$ which dsh
/Users/zhm20001/Library/pnpm/bin/dsh        ← PATH 目录之一
$ cat $(which dsh)
#!/bin/sh
exec node /Users/zhm20001/deepseek-harness/apps/cli/lib/bin.js "$@"
                                            ← 整个"命令"就 3 行脚本

没有注册表,没有系统数据库,没有后台服务。~/Library/pnpm/bin 恰好在你的 PATH 里,里面躺着谁,谁就是命令。

3. 四层管线:源码如何变成命令

把「clone 下来的源码」变成「任何目录能敲的命令」,中间隔着一条四层管线,每层有自己的产物、自己的目录、自己的更新命令:

层产物落在哪谁/什么命令负责
① 源码git 工作区(tracked 文件)你的 clone 目录git clone / git pull
② 依赖node_modules(第三方包)clone 内,不进 gitpnpm install
③ 构建产物lib/(编译出的 JS)clone 内,不进 gitpnpm run build
④ 命令一个可执行文件PATH 上某目录"注册"(见第 4 节)

三个推论,每个都能解释你这次事故的一面:

  • 层与层不联动:更新第①层不会碰②③④。pull 完不 install/build,跑的还是旧产物;build 完不更新第④层的指向,命令 behavior 不变。
  • git 只认识第①层:clone/pull 只搬运 git 追踪的文件。②③ 层的目录都在 .gitignore 里,④ 层更是 git 世界观之外的概念。
  • 验收要对层:查第①层用 git log --oneline -1;查第③层看 lib/ 的时间戳;查第④层用 dsh --version。一个版本号不对,先定位错在哪一层,再动手。

4. 回答你的三个问题

Q1:为什么 clone 完没有 dsh 命令?

因为 git clone 只做第①层,而且做完了也只有第①层——②的 node_modules、③的 lib/ 都不在 git 里,要你手动 install + build;④的注册更是没有任何工具会"顺带"帮你做。git 是版本管理工具,它不知道 PATH 是什么。

补充一个容易混淆的点:clone 完就能跑的 pnpm dsh 不是全局命令——它是仓库 package.json 里 scripts 字段定义的脚本(用 tsx 直接吃①层源码),只在仓库目录内、通过 pnpm 调用才存在。

Q2:"注册为命令"到底是什么操作?

就是第②节那句话:在 PATH 目录里放一个可执行文件。你做过两次,方式不同:

  • 8-22 的手动打包:把①②③层的成果打成压缩包,pnpm add -g 把它复制进 pnpm 的全局区域,并在 PATH 目录生成入口文件。复制是快照——这就是它永远停在 0.1.0-rc.5 的原因。
  • 这次的 wrapper:PATH 目录里只放一个 3 行脚本,exec node 直接跑你 clone 里的③层产物(apps/cli/lib/bin.js)。指向不是快照——每次 pnpm run build 之后,全局命令自动就是新的。代价:一条依赖链(路径写死在脚本里,若未来 apps/cli 挪位置要改)。

Q3:选 release(pnpm add -g)还需要手动注册吗?为什么?

不需要,但注册这件事仍然发生了——只是安装器替你做了。npm 包的清单文件里有一个 bin 字段,dsh 的(apps/cli/package.json)写着:

"bin": { "dsh": "lib/bin.js" }

这是包作者预先写好的注册说明书:"装我的时候,请把 dsh 这个名字接到包内的 lib/bin.js"。pnpm add -g 读它、照办、把入口放进 PATH 目录(pnpm install 文档)。所以三种方式底层是同一个操作,区别只在谁执行、指向哪:

git clone + wrapper手动打包(8-22 的做法)pnpm add -g(release)
注册动作你手写 wrapper你打包,安装器建入口安装器读 bin 字段自动建
④层指向你 clone 的③层(活)打包时的拷贝(死)npm 下载的拷贝(死,随重装刷新)
更新方式pull + install + clean + build重新打包重装重新 add -g
版本跟 master(可到未发布版)冻结跟 npm 已发布版(滞后)
能魔改✅ 改完 build 即生效❌❌
适合谁读源码/魔改/追最新—(两头不占,弃)只想用命令

顺带一句:pnpm dlx/npx 可以临时借用一个命令而不在 PATH 留文件——第④层的另一种形态,知道即可。

5. git 四件套:更新第①层的机械

命令一句话机制在你事故里的角色
clone首次下载:整份历史 + 铺出工作区起点(只完成①层)
pull= fetch(下载新提交进 .git)+ merge(把本地分支移过去)。不是同步按钮,是一次合并;本地脏文件与传入改动重叠时,拒绝执行并打印错误凶手:拒绝被你看漏,落后 1933 提交而不自知
diff工作区 vs 最近提交的差异清单pull 前先看自己改了什么
stash把脏修改压进一个栈,工作区瞬间变干净;stash pop 取回;restore 则是直接丢弃修复:想留的 stash,不要的 restore,然后 pull 畅通

两条习惯,防"看漏"重演:pull 永远配 --ff-only(只允许纯快进,有分叉就明说,不悄悄制造 merge commit);pull 后必验收——git log --oneline -1 或 git status 的 ahead/behind 标注,用眼睛确认①层真的动了。

6. pnpm 三件套:更新第②③层

  • pnpm install:按 lockfile 把 node_modules 同步到当前源码需要的依赖(这次跨 1933 提交,跑了 4 分钟);
  • pnpm run clean:清掉旧构建产物和已删除包的残留(这次清了 233 个路径)——防旧文件混进新版本;build:tsc + tsdown 编译出③层的 lib/。

于是你的追更口诀(配 wrapper 方案,④层自动跟上):

git pull --ff-only && pnpm install && pnpm run clean && pnpm run build
dsh --version        # 验收:④层读到的版本 = ①层刚拉到的版本

压缩成一页的速查表在 dsh 追更速查表,以后忘了翻它,不用翻这节课。

检索练习

Q1. 在终端敲下 dsh 并回车,shell 实际做的第一件事是?

没有登记数据库:PATH 就是一串目录名,shell 挨个翻,第一个命中就执行。所以"命令存在"等价于"PATH 某目录里有这个文件"。

Q2. 为什么 git clone 完成后没有全局 dsh 命令?

clone 连②③层(node_modules、lib/)都不给——它们不进 git;④层注册更是 git 世界观之外的事。能用 pnpm dsh 是仓库内脚本,不算全局命令。

Q3. pnpm add -g 安装后命令"自动出现",底层机制是?

bin 字段是包作者预写的"注册说明书",安装器照办——和你手写 wrapper 是同一个操作,只是执行者从你换成了安装器,指向从活源码换成了下载拷贝。

Q4. 8 月 22 日手动打包的全局 dsh 为什么永远停在旧版?

复制即快照:仓库此后 pull/Build 多少次,都不会写进那份拷贝。wrapper 改成"指向"后才重新联动——但只联动到③层,build 不能省。

Q5. 本地脏文件与传入改动重叠时,git pull 会怎样?

pull = fetch + merge,merge 对重叠修改拒绝执行——保护你的未提交工作。代价是失败只写在终端那一屏:不看输出,就以为更新过了。事后一律用 git log -1 验收。

动手验证(10 分钟,全部零风险)

  1. 亲眼看穿一个命令:which dsh && cat $(which dsh),再 echo $PATH | tr ':' '\n' | head -8——找到 wrapper 所在目录在清单里的位置。
  2. 验证"指向不冻结":在 /tmp 下跑 dsh --version(确认与 cwd 无关);然后 ls -l apps/cli/lib/bin.js 看构建时间戳——它就是全局命令此刻读的文件。
  3. stash 演练:在仓库里 echo test >> docs/cordis-tutorial/01-first-plugin.zh.md,依次跑 git diff(看到自己的改动)→ git stash(工作区变干净)→ git stash pop(取回)→ git restore docs/cordis-tutorial/01-first-plugin.zh.md(丢弃)。四个状态亲手过一遍。
  4. 体会发布节奏:pnpm view @deepseek-ai/dsh version 对照 GitHub master 的版本号——哪个更新?这对"选 clone 还是选 release"意味着什么?

本课收获

  • 命令 = PATH 上一个可执行文件;"注册"就是把文件放进 PATH 目录,无任何魔法。
  • 四层管线(源码→依赖→构建→命令)每层只认自己的更新命令,层间不联动;排故障先定位层,再动手。
  • clone 只给①层;release 的"自带命令"是安装器替你执行了④层(依据包清单的 bin 字段);wrapper 是把④层指向自己 clone 的③层——追更 + 魔改的最优解。
  • pull 是合并不是同步:配 --ff-only,执行后必用 git log -1 验收;脏文件挡路时 diff → stash/restore → 再 pull。
