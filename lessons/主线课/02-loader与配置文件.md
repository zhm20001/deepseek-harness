# 02 — Loader 与配置文件：谁决定一家店的存在

> 本课回答：装哪些插件、各配什么参数、怎么改，由谁决定、放在哪。上一课说"装载由 Loader 发起"，本课看清它怎么发起。核心一句话：**插件名单是一份数据文件，Loader 是读它、改它、存它的那套系统。**

## 逻辑层

### 一、配置行即数据（必记）

**大白话**："装哪些插件"不写死在代码里，而是写在一份配置文件（cordis.yml）里。每一行是一条**数据**：叫什么（插件模块）、什么参数（config）、需要谁（inject）、开不开（disabled）。因为它是数据不是代码，**增删改插件 = 改数据行，不用改任何代码**。

**术语**：一行 = Entry；管理这些行的系统 = Loader。

**例子**：dsh 的全部插件组合都由几份 YAML（bundle / profile / 你的配置）决定，同一个二进制能长出命令行、网页、SDK 三种形态，靠的就是改数据不改代码。

**推论**：换插件、加插件、关插件，通常只是一行配置的事——dsh 的"可组装"来自这里。

### 二、Loader 做三件事：读、改、写回

1. **读**：把数据行变成真商户——按名字导入模块，连同参数交给上一课的内核开业。谁先谁后？还是"需求是否满足"，Loader 不排顺序。
2. **改（patch）**：基础名单之上，任何人都能提交"改行指令"：按 id 找到某行、覆盖它某个字段、或插入新行。指令**按层依次生效，后层胜出**——所以捆绑包给的默认值，你的配置总能覆盖。找不到目标行就告警跳过，不报错。
3. **写回（write-back）**：反过来，运行期的变更（网页上改配置、代码里停用插件）也会**反写回数据文件**，重启进程后依然生效。"读它、改它、存它"才是"配置即数据"的完整含义。

**推论**：三件事合起来，配置文件就是整个系统"活的状态"——它既是启动说明，也是运行期变更的存档。

### 三、`!!js`：让配置文件能"现场算一个值"

**大白话**：配置文件是写死的文本，但有些值依赖"这台机器"（用户名、路径、开关）。`!!js` 允许在配置里嵌一小句 JavaScript，装载那一行时**当场计算**，结果当作配置值。例：`user: !!js "process.env.USER"`——同一份文件，每台机器自动适配。

**限制**：只允许在**配置值**和**禁用开关**两处写；其余地方必须写死——否则配置文件就成了任意代码的入口，这个口子不能开。

### 四、热更新（HMR）：改文件不重启

**大白话**：改**插件代码**文件 → 把这个插件整个换新（旧的下、新的上；换失败自动回滚到旧版）；改**配置文件** → 重读名单、按差异增删改商户；改**框架本身** → 才需要整个进程重启。

**推论**：日常"改一点、看一眼"的开发循环，靠的就是"插件文件可热换、配置文件可热读"这两条。

### 五、行级隔离（一句话预告）

每行配置还能声明"这块服务单独立门牌"——为多 agent 互不串线预备的机制，下一课正式登场。

## 记住什么 / 不用记什么

**记（4 个）**：配置行即数据（增删改插件 = 改数据）；patch 按层生效、后层胜出；write-back（运行期变更落盘）；`!!js` 只许在配置值和禁用开关两处。

**不用记**（卡住回溯）：Entry / EntryGroup / EntryTree 类名、`applyEntryPatches`、`interpolate`、LocalRealm / GlobalRealm、HMR 的缓存清理细节——地址见下表。
