# 04 — Session 事件日志：agent 的"只进不改"流水账

> 本课回答两个问题：模型看到的一切，为什么必然能从磁盘上的日志重建？"改了历史"为什么被禁止？接缝：上一课给了读插件的钥匙（三问检验），从本课起进入插件正文——第一个精读的是所有插件共享的那间"档案室"，也就是主线不变量③（模型可见 ⟺ 可重建）的老家。

## 逻辑层

### 一、档案室：为什么"只写不改"（append-only 日志 = 唯一真相源）

**大白话**：楼里有一间档案室——agent 说过的每句话、做过的每件事，都按顺序写成一条记录放进去。纸只进不出：谁也不许撕页，不许涂改；想"改"，只能再添一条新记录，说明改了什么。这么死板的原因：agent 是替你动手干活的，它看过什么、被批准过什么、删过什么，将来都要能对证，而唯一可靠的对证物就是一份从没被改过的流水账。

**术语**：这份流水账叫 session 事件日志，"只写不改"的行话叫 **append-only**。内存里的档案是一个私有的有序数组，外界唯一入口是追加（`append`）；每条记录自动盖两个章：序号 `seq`（从 0 开始连续编号）和时间。

**例子**：你中途按 Esc 取消一次回答。模型已经吐出的半截话不会被撕掉——照样记一条"助手消息（被打断）"，下一轮模型仍然看得见自己说过半截话。

**推论**：所以"改历史"不是被禁止的操作，而是**不存在的操作**——没有删除、没有修改，只有追加。连"用户在界面上删一条消息"也是追加一条"此消息已删"的记录（真实事件 `feedback/message-delete`）。

### 二、上镜名单：模型可见 ⟺ 可重建

**大白话**：模型每轮看到的"聊天记录"，不是另存的一份文件，而是当场从档案室**誊**出来的。誊写有份名单：只有五种记录会上镜（系统提示 / 用户消息 / 助手消息 / 工具结果 / developer 消息）；其余的（"第几轮开始""这次调用挂了"）只留档，不上镜。

**术语**：誊写叫**派生**（`deriveMessages`）；五种上镜记录合称表面事件（surface events）；每条上镜记录在入档时必须声明自己怎么上镜——正常排在队尾，或者"顶替第 X 到第 Y 条"。少声明，追加当场被拒绝。

**例子**：上下文太长触发压缩（compaction）时，旧消息一条不删：追加一条"摘要"，并在上面标明顶替了哪几条。誊写时被顶替的不誊、摘要上镜——档案原封不动，模型看到的变了。

**推论**：把上下文变短也是一次追加，不是一次修改。这就是不变量③的完整含义：看不见的一定没进档案，进了档案的一定能重新誊出来；而且这份强制不长在文档里，长在"追加"这个动作本身上。

### 三、词表与"不认识的字"（事件即词表；ignorable）

**大白话**：档案里每条记录开头写一个词，说明这条是什么（"用户说""工具返回""这轮结束"……）。这个词表公开而且**谁都能添词**：审批插件添了"审批已请求""审批已决定"，待办插件添了"待办已写"。添词带来新麻烦：老版本的程序打开新版本写的档案，碰到不认识的词怎么办？

**术语**：词表叫 `SessionEventMap`（事件类型表），插件用类型声明合并往里添词；每条记录可以带一个"可跳过"角标（`ignorable`）。默认**不带**——遇到不认识的记录，宁可整卷拒读，也不悄悄跳过。

**例子**：老版本 dsh 读到一条没带角标的 `todo/write`，直接拒绝："这份日志是更新的程序写的，我不敢乱读。"

**推论**：宁可拒绝，不可错读。错读等于拿一份残缺的历史继续工作，比当场停机危险得多。也正因如此，添词不需要升档案版本号——角标就是词表扩充的兼容机制。

### 四、磁盘上的两条纪律（历史只进不退）

**大白话**：内存里的档案断电就没了，所以有位誊写员把它抄上磁盘。纪律一：每抄一批就"落锁"，断电也不丢已经抄下的。纪律二：档案格式升级时**另立新柜**，旧柜原样封存，谁也不许回去改。

**术语**：誊写叫**持久化**，它自己是个普通插件（听 `session/event` 广播抄写，听 `session/flush` 落锁）；档案格式版本是单个只涨不改的整数（当前 4）；升级叫**迁移**，v0→v1→…→v4 每一步是一个独立的迁移包。

**例子**：磁盘上同一个会话可能并排躺着 `session.jsonl`、`session.v1.jsonl`、`session.v2.jsonl`……读取时沿升级链一步步翻译到当前版本。

**推论**："只进不退"在两层同时成立：内容层不许改写（只有追加），文件层不许覆盖（升级只加新文件）。连崩溃恢复也是追加式的：崩溃留下的半截回合不删除，恢复程序补几条收尾记录说明它是怎么结束的。

### 五、三问检验：第一个真实插件

拿三问读 `@deepseek-ai/dsh-session`：**provide** 什么——`ctx.sessions`（档案室的内存前台：开档案、查档案）；**inject** 什么——`typert`（把"按 id 找会话"登记进全楼的查号台）；**on** 什么——无。它是四个 `session/*` 广播的**发声者**，不是听众；持久化、统计、界面这些听众插件，各听各的。

## 记住什么 / 不用记什么

**记（4 个）**：append-only 日志 = 唯一真相源；模型可见 ⟺ 可重建；事件即词表（谁都能添词，不认识的词宁拒勿跳）；历史只进不退（改 = 追加，升级 = 新柜）。

**不用记**（卡住回溯）：`Session` / `SessionStore` 类名，`append` / `deriveMessages` 函数名，`SurfaceOp` / `sourceEventSeqs` 字段名，`SESSION_FORMAT_VERSION` 的具体数字，`KNOWN_SESSION_EVENT_TYPES` 的完整名单，fork 与继承前缀的细节——全部是上面四条规则的具体实现。
