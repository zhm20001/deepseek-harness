# 11 — 委派与并行：活儿怎么分出去、收回来

> 本课回答：活儿怎么分出去、怎么收回来？subagent、后台任务、工作流三者的边界在哪？接缝：03 课的 Scope 在这里长出"分身"；05 课"通知不可否决"、09 课"票根逻辑"在本课第三次、第四次兑现。

## 逻辑层

### 一、subagent：同一句话，叫得动千军万马

**大白话**：主 agent 手里有个"派活"工具。它说"派个分身去查 X"——分身可能就在同一间屋里转身干活，也可能被派到另一台机器、甚至另一个产品的大门口。**派活的那句话一模一样**，分身住在哪，说话的人不知道。

**术语**：`ctx.subagents` 是**名册制**：每个 Provider 报一个名字，调用者按名点将。两种活儿：一次性派活（run 到结束交结果）和**可续派**——分身有自己的档案和收件箱，可以持续接新指令。

**例子**：Provider 家族：同进程分身（fork / spawn）、跨进程协议（ACP）、还有 Claude Code 与 Codex 这样的外部产品——内部十万八千里，对工具来说是同一块招牌。

**推论**：09 课票根逻辑的又一兑现：传话（sendMessage）可以隔着边境走，接口不暴露"分身是不是本地的"。递归层数也写进分身的档案头（04 课），重启不丢。

### 二、jobs：后台活儿的统一登记处

**大白话**：有些活儿不该让主 agent 干等（长测试、慢下载）。登记处给每件后台活儿发一个**号牌**，产出写进一个**环形的本子**——模型凭登记处的书签接着读，旁观的界面按绝对位置读，互不打扰。任务比干活的插件活得久：插件卸载了，号牌和记录还在，直到主人来收尸。

**术语**：`ctx.jobs`；每件任务一条**有界环形输出**（模型的书签和旁观者的偏移读同一串字节，互不挤占）；结算先到先得，一件活儿只有一张终局记录。

**例子**：模型启动长测试，拿到号牌就回去继续干别的，过会儿用"读输出"工具跟着进度走——不必把整份日志塞进对话。

**推论**："登记处"是 04 课档案室的亲戚：状态不在干活的插件手里，在公共登记处手里——所以谁都能查，插件死了账还在。

### 三、workflow：把编排放进剧本

**大白话**：前两样是"派一件活"；工作流是"照**剧本**派一连串活"——脚本里依次或并行地喊多个 agent、汇报进度、最后交结果。注意：剧本喊的每一声都只是**播报**，谁也不能靠听播报改变剧本走向。

**术语**：`ctx.workflowEngine`；阶段、日志、分身起止全是 emit——契约原话"观察类生命周期事件不暴露运行控制"；执行剧本的 Provider 另有其人（跑在代码运行时里）。

**例子**：`workflow/phase` 只是给观察者分组的进度字幕，没有任何执行含义。

**推论**：观察（通知域）与控制（剧本本体和它的工具）分家——05 课"选域先于选包"的第三次落地。

### 四、边界：subagent 是星形，team 是网状

**大白话**：subagent 管"一对多派活"；agent-team 管"多对多协作"——在派活之上加了三样公共设施：**名册**（谁在队里）、**任务板**（活儿挂板上认领）、**信箱**（成员间互发消息）。

**术语**：roster / task board / mailbox——占位句的准话。

**推论**：委派是星形（父→子，树状收口），协作是网状（成员互认）。选哪个，看你画的是树还是网。

### 五、三问检验：派活的工具

拿三问读 `dsh-tool-subagent`：**provide** 什么——无新招牌（把"派活"工具挂上 tools 名册）；**inject** 什么——`['tools', 'subagents', 'systemPrompt', 'sessionProjections']`；**on** 什么——名册变动广播（有 Provider 来去，工具说明里的"可选分身名单"就实时刷新）。纯消费者 + 活菜单：它自己不派活，只把派活的权力翻译给模型。

## 记住什么 / 不用记什么

**记（4 个）**：subagent = 同一接口、极端不同的 transport（名册点将；可续派有档案有收件箱）；jobs = 后台统一登记处（号牌 + 环形输出，活得比插件久）；workflow = 编排剧本（播报不可否决）；委派星形、协作网状（team 多出名册/任务板/信箱）。

**不用记**（卡住回溯）：各 Provider 包名、JobKind / JobChannel 的枚举、环形输出的实现细节、脚本 API 的函数名、深度预算的具体数值——全部是四条规则的具体实现。
