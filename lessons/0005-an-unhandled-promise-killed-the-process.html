Lesson 0005 · 真实事故解剖

一张没兑付的欠条,杀死了整个程序

目标:15 分钟后,你能拿一段崩溃栈从下往上读出凶手;能用自己的话解释 unhandledRejection 为什么致命;并且下次验收 AI 写的插件时,知道专门去检查一个地方——定时器和回调里的 Promise,有没有人接住它的失败。
这不是编的教学案例。2026-08-27 下午,你自己的 dsh-usage-board 插件两次把整个 dsh 进程杀掉(exit 1),看起来"像是换本地模型导致的"。完整调查记录在 事故文档 里;本课把它的编程原理讲透——你已经是插件作者了,这类事故以后要能自己认出来。

1. 凶案现场:崩溃栈要倒着读

程序猝死时留下的遗言叫崩溃栈(stack trace):一张"谁叫谁做事"的清单。读法是从下往上——最下面是起点,最上面是死因。这次事故的遗言:

dsh: fatal load failure: Error: session "undefined" is not live in this store
    at Proxy.liveEntryFor (宿主 session 服务的内部校验)   ← 4. 死因:发现对象不对
    at Proxy.flush (宿主的 flush 函数)                    ← 3. 它调用了内部校验
    at Object.flushSession (你的插件 dsh-usage-board)     ← 2. 凶手:传错了东西
    at TelemetryCollector.flush (你的插件)                ← 1. 起点:批量落库开始
    at Timeout.<anonymous> (一个 250ms 定时器)            ← 0. 引信:时间到了

用人话倒着念一遍:一个定时器到点了 → 插件开始把统计数据写进数据库 → 写之前先请宿主把日志刷盘 → 宿主一看手里的东西不对,当场掀桌 → 整个进程退出,退出码 1。下一节解释每个环节里藏着的专有名词。

2. 三张名词卡(零基础版)

名词卡一:函数签名 = 插头与插座

每个函数声明自己"要收什么样的东西":flush(session: Session) 意思是"我只收一个 Session 对象"。这叫签名(signature)。调用时该传什么,就像插头该配什么插座——形状不对就插不进去。但 JavaScript 运行时不检查形状:你硬把一根 字符串(比如 "session-b46b…")插进去,它不报错,直到宿主内部去读 session.id 时才发现——字符串身上根本没有 .id,读出来是 undefined,于是报错 "session \"undefined\" is not live"。类型不匹配不是当场爆炸,而是延迟到"用的时候"才爆炸——这是它危险的根源。

名词卡二:Promise = 一张欠条

异步操作(等磁盘、等网络、等模型吐字)不会立刻给结果,只先给你一张凭证,叫 Promise(可译"承诺")。三种状态:pending(还没兑现)、fulfilled(兑现了,拿到结果)、rejected(拒付——出了错)。配套语法:

  • await 欠条 = "站在这里等它兑现,拒付就把错误抛给我处理";
  • 欠条.catch(处理函数) = "我不等,但拒付了叫我"——接住失败的人。

关键规则:一张 rejected 的欠条,如果从头到尾没有任何人 await 或 .catch 它,就是 unhandledRejection(未处理的拒绝)。而 Node.js 从 15 版起对 unhandledRejection 的默认处罚是:直接杀死整个进程。一张废纸,一条人命。

名词卡三:fire-and-forget = 把欠条扔进抽屉

"发射后不管"——代码发起一个异步操作,既不 await 也不 .catch。写法常见两种:doWork() 光调用不看返回值,或 void doWork() 明确表示"我故意不看"。它不是天生错误——但等于把欠条扔进抽屉:兑现了最好,拒付了没人知道。在这次事故里,扔欠条的地方是个定时器(setTimer(250ms, () => void this.flush())):定时器回调不属于任何"等人"的流程,错误一旦在里面发生,就再也无人接手。

3. 逻辑链:六步杀死一个进程

现在把名词卡串起来。每步左边是真实机制,右边是修复后的代码对照(都在你仓库里,commit 7750c36):

步发生了什么欠条比喻
①模型发出工具调用,插件收到 session/event,折算出第一批待写行统计员开始记账
②队列闲置 250ms,定时器到点,执行 void this.flush()定时闹钟响了,把欠条扔进抽屉
③flush 先 await flushSession(sessionId)——但把字符串传给了要Session 对象的宿主函数拿错了票据去柜台
④宿主读 session.id 得 undefined,抛出错误;async 函数里一抛错,返回的 Promise 变 rejected柜台拒付,欠条作废
⑤调用方是定时器回调,当初 void 掉了返回值——没有 catch,没有 await抽屉里的废纸无人过目
⑥Node 判定 unhandledRejection;dsh 的 fail-loud 策略打印一行诊断,exit(1)银行连夜倒闭

注意②和③的时间差骗局:闹钟在"模型刚发出工具调用后 250ms"才响,所以闪退看起来发生在"工具执行时"——其实是落库定时器到点。事故文档里还列了另外两个巧合(本地模型首字要 131 秒、重写插件后首次真对话),三个巧合叠出"换本地模型导致的"这个错觉。调试第一课:相邻 ≠ 因果。

4. 为什么 TypeScript 和 205 个测试都没拦住?

你可能会问:签名不匹配,编译器不是应该报错吗?测试不是全绿吗?这是本课最重要的一问。

TypeScript 被骗了。你的插件为了"零宿主依赖",在 src/index.ts 里手写了一份宿主服务的镜像类型(HostContext),其中把 flush 的参数写成了 string。TS 只检查"你的调用 vs 你声明的类型",不检查"你声明的 vs 宿主真身"。镜像写错,编译器就替你把错误背书了。这正是第 4 课契约方法的反面案例:手写契约一旦与真身失配,所有检查都会越过真错误。

测试也被骗了。205 个测试里,宿主是用 mock(替身)模拟的——而这个 mock 也是照着同一份错误镜像写的,flush("字符串") 在替身身上"能跑通"。实现和测试一起错,红灯永远不亮。镜子照镜子,照不出真脸。

验收视角:AI 给你交付带"手写接口镜像 + mock 测试"的插件时,要问一句——"镜像和宿主真身之间,有没有哪怕一条对过账的测试?"没有的话,签名漂移就全靠线上爆炸来发现。这也解释了为什么"装好插件、看到历史数据进库"不等于没病:那条路(backfill)不经过出错的屏障。

5. fail-loud 与两层防线

宿主 dsh 对 unhandledRejection 的策略叫 fail-loud(响亮地失败):与其带着说不清的状态继续跑,不如当场死给你看,还留一行遗言。对一个 agent 宿主这是理性的——半死不活的状态可能悄悄写坏你的数据。但它的代价是:任何一个插件的任何一张废欠条,都能杀死全家。

所以正确分工是两层:

  • 宿主层(没变):进程级错误,响亮地死;
  • 插件层(这次修的):自己发起的异步操作,自己接住失败——修复后定时器入口全部走 flushSafe():flush().catch(err => 记入 ingestion_error)。一次落库失败,最多损失一批统计数据并留下案底,不可能再杀宿主。

检索练习

Q1. 一个 rejected 的 Promise 从头到尾没人 await 或 .catch,新版 Node.js 默认会怎样?

Node 15 起默认策略就是抛出未捕获异常、进程退出。"只警告不退出"是老版本行为——很多教程还停留在那个时代。

Q2. 这次事故的根因(第一因)是哪一个?

模型慢只是巧合之一;锁库从未发生。第一因是签名错配,后面每一步(定时器、无人接住、fail-loud)只是把它放大成进程死亡。

Q3. 205 个测试全绿,为什么线上还是崩了?

替身和实现照着同一份写错的"说明书"长,自然一起通过。需要的是让契约对一次"真身"——例如一条对照宿主真实类型编译的测试。

Q4. 修复里的 flushSafe() 体现了什么原则?

接住 ≠ 吞掉:失败被记入 ingestion_error 表,损失有案可查。"静默吞掉"和"立刻退出"恰好是两个反例。

动手验证(10 分钟)

  1. 看修复本身:cd ~/projects/usage-dashboard/dsh-usage-board && git show 7750c36。只看两处——src/index.ts 里 get(sessionId) 那三行(根因),telemetry.ts 里 flushSafe()(防线)。对着第 3 节的六步表,指出各自掐断了哪一步。
  2. 亲手制造一次"欠条拒付":在 Node 里跑 node -e "Promise.reject(new Error('废欠条'))",观察进程退出码(echo $?)。再跑 node -e "Promise.reject(new Error('废欠条')).catch(e => console.log('接住了', e.message))" 对比。
  3. 检查你另一个插件(mytool-dsh-notes)有没有同类隐患:搜一遍定时器/事件回调里的异步调用,看返回的 Promise 是被 await、被 .catch,还是被扔进了抽屉。

本课收获

  • 崩溃栈从下往上读:最底是引信,最顶是死因;中间离你代码最近的那一帧,通常就是凶手。
  • 三张名词卡:签名=插头插座(JS 运行时不查形状,延迟爆炸)、Promise=欠条(rejected 且无人接=unhandledRejection=进程死亡)、fire-and-forget=把欠条扔抽屉。
  • 手写镜像类型会骗过编译器,mock 会跟着一起错——契约必须对过一次真身。
  • 验收清单 +1:插件里定时器/回调发起的异步操作,必须有 .catch;新插件装好后必须做一次"真路径冒烟"(真实对话一次),不能只看安装期的数据。

下一课预告

这次事故还留了一个尾巴:统计库有"数据缺口"(崩溃期间与未装插件期间的会话不会自动补录),需要给插件加一个 rescan 入口——那会是一次完整的"从验收发现的问题倒推设计"的练习,正好接上第 4 课的契约方法。
