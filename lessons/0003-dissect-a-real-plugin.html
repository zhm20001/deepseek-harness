Lesson 0003 · mytool 实战

解剖一个真实插件:mytool-dsh-notes

目标:15 分钟后,你能对着你自己项目里那个 AI 写的 dsh 插件,按部位逐项验收——每个部位该有什么、缺了会长什么样。
上节课预告了「四条集成路径怎么选」。我们没有纸上谈兵——过去几个 ticket 里,你的 mytool 真的走完了其中一条。本课解剖的不是一个教学示例,是你仓库里真实跑通、81 个测试全绿的那个插件:~/projects/mytool/dsh/src/service.ts。

1. 四条路,我们选了哪条、为什么

路径适合代价
直接调 LLM API SDK一次性文本任务没有 agent 生态:工具、会话、重试全自己来
dsh 客户端(JSON-RPC / ACP)驱动现成 agent 干活能力受限于已有工具面
写 tool 插件(本次)域逻辑 + 判断混合要懂插件模型(正是本课)
内嵌 agent-spine自己组装 agent 服务端自由度最大,维护最重

mytool 的域是「硬存储操作(save/find/restore)+ 软判断(整合)」混合:硬的部分适合做成工具让 agent 调,判断留在对话里——所以选插件路,且不碰 loop 一行。

2. 装载:外部插件怎么进 dsh

插件住在仓库外(~/projects/mytool/dsh),装载靠两件事:

  1. patch 追加一行(第 2 课的语法原样可用):- insert: - id: notes / name: /Users/zhm20001/projects/mytool/dsh——绝对路径行,tsx 直载 TS 源码,不用先 build。
  2. 裸包名靠 link: 依赖解析:插件代码里 import … from '@deepseek-ai/dsh-tools' 能找到 harness 源码树,是因为插件包 node_modules 里放了 link: 依赖指向 harness 包目录——同一个 realpath,同一个模块实例,没有版本漂移。
验收问法:「AI 给我的安装步骤,在干净机器上能不能从零跑通?」外部插件的装载路径是第一道坎;跑 --dump-config 看到你的行出现在最终清单里,才算装上了。

3. Service 骨架:插件的本体

export class NotesService extends Service {
  static inject = ['tools', 'llm']      // 硬依赖:tools 不在,插件整个不装
  static Config = Schema.object({        // 可从 cordis.yml 校验的配置面
    notesDir: Schema.string().required(),
    integrate: Schema.object({ provider: … 'deepseek-official', model: … 'deepseek-chat', … }),
    strongScoreThreshold: Schema.number().default(15),
    maxTags: Schema.number().default(6),
  })
  constructor(ctx) {
    super(ctx, 'notes')                  // 服务名 → 全局 ctx.notes
    for (const register of [saveTool, readTool, …]) ctx.effect(() => register(ctx, this), …)
    ctx.inject(['skills'], sctx => { … })  // 可选依赖:有 skills 服务才注册技能
  }
}

四个部位,验收各问一句:inject 声明对吗(多声明会让插件无故 pend,少声明会在运行时炸)?Config 里部署会变的量(provider、路径、阈值)是不是都在,还是被写死在代码里?注册是否全走 ctx.effect(否则卸载漏清场)?「有则用无则跳」的依赖是不是用了 ctx.inject 而不是硬声明?

4. defineTool 五面:note_integrate 做标本

面作用验收问
parameters模型看到的参数契约(required / enum / 描述)模型能只靠描述用对吗?
output.schema结果的类型契约(回放 / UI 用)字段是否 additionalProperties:false?
output.render给用户看的纯函数摘要是不是纯函数?会不会把全文塞给模型?
presentationMeta + presentResultdiff 卡:meta 里持久化,呈现时读回,错误返回 undefined呈现坏了会不会连累工具本身?
execute委托 service;抛错 = isError 结果有没有多余的 try/catch 把失败吞成假成功?

5. ctx.llm 直调五件套(背下来当清单)

const messages = [createUserMessage({ content: […], source: { kind: 'plugin', plugin: 'mytool-dsh-notes' } })]
using callDeadline = deadline(req.signal, config.timeoutMs, 'NOTE_INTEGRATE_TIMEOUT')
const options = deepFreeze({ provider, model, temperature, messages, system, signal })
for await (const part of ctx.llm.stream(options)) { assembler.push(part); req.signal.throwIfAborted() }
const err = finishError(finish)   // stop→过;error/aborted→带 code;max-tokens/tool-calls→具体信息
  1. 来源标记(source.plugin)——日志里能看出这次调用是谁发起的;
  2. using + deadline——超时在异常路径也释放;
  3. deepFreeze——请求一经装配不被偷改;
  4. 流式循环里 throwIfAborted——取消即时生效;
  5. finishError 翻译——终止原因变成该报的错,而不是笼统一句 failed。
AI 写 LLM 调用时最常缺 2 和 5:没有 deadline(挂死),不区分 max-tokens 和真错误(误诊)。对着这五件逐一勾。

6. 一个真实的平台约束:为什么没有自定义事件

原设计想仿 session-title-llm 发一个自定义事件记录 LLM 请求。实现时撞墙:仓外插件的事件类型不在持久化重载的事件白名单里——落盘了,会话日志重载直接被拒绝。处置:可重建性改由标准 tool 事件承载(材料在调用参数、模板版本在结果、前版在 .bak),spec 补了带日期的追记。这示范了验收者最该有的一种反应:发现「设计说的」和「实现做的」不一致时,要的是文档化的修正,不是假装一致,也不是悄悄删需求。

检索练习

Q1. 插件声明了 static inject = ['tools', 'llm'],但目标 profile 没有 llm 服务。会发生什么?

inject 是硬门:依赖不齐,插件整个不装。想要「有则用无则跳」要用 constructor 里的 ctx.inject(['skills'], cb)——mytool 对 skills 服务就是这么做的。

Q2. 外部插件源码里 import '@deepseek-ai/dsh-tools' 能解析,靠的是什么?

link: 依赖把裸包名解析到 harness 源码树,同一 realpath 同一模块实例——外部源码插件不发布也能用上仓内的服务。

Q3. note_integrate 的 execute 里 LLM 调用超时抛错,工具结果会怎样?

「execute 抛错 = isError」是框架契约;包一层 try/catch 反而可能把失败吞成假成功。fail loud 是默认姿态。

Q4. AI 在 GenerateOptions 里加了 purpose: 'note-integration',类型检查会?

'compaction' | 'session-title' 是闭字面量 union,声明合并扩不了它。外部插件直调留空即可——这是「仓内扩展点 vs 仓外用法」的边界感。
